## Keputusan desain kunci
- bankwire pakai tabel asosiasi shop terpisah (`bankwire_account_shop`), BUKAN multishop
  bawaan ObjectModel → tabel lang cukup `(id_bankwire_account, id_lang, custom_text)`
  tanpa `id_shop`.
- Query mentah (`SELECT a.*`) di getActiveBanks/getAllBanks/getBankForOrder → custom_text
  via **LEFT JOIN** `bankwire_account_lang` pada id_lang konteks (LEFT: bank tanpa baris
  lang tetap tampil).
- reservation_days: kolom `reservation_days INT UNSIGNED DEFAULT 0` di `bankwire_account`
  (0 = ikut global). Global = `Configuration BANKWIRE_RESERVATION_DAYS` (default 7, seperti
  ps_wirepayment). Efektif = `bank.reservation_days ?: global`.

## fix-core-mail-template-clobber
Status: diterapkan

**Pemblokir** dari vonis psm-validate 2026-09-08 (`adv-core-mail-template-clobber`, severity error,
berlaku di 1.7.8/8.1/9.1). Bukan penambahan fungsi — perbaikan cacat.

### Akar (diverifikasi di container, bukan diasumsikan)

`installOrderState()` **selalu** early-return di toko standar: core mengirim `PS_OS_BANKWIRE` =
OrderState 10, `module_name = ps_wirepayment`, `template = bankwire`. Module tak pernah punya
state sendiri — ia menumpang. Lalu `copyMailTemplates()` menimpa `_PS_MAIL_DIR_/<iso>/bankwire.html|txt`,
yaitu file yang dipakai state 10 untuk order `ps_wirepayment` juga.

`OrderHistory` memanggil `Mail::Send(..., _PS_MAIL_DIR_, ...)`; `module_name` hanya dipakai
menggabung `extra_mail_vars`, **bukan** untuk resolusi template. Jadi email order `ps_wirepayment`
membaca file yang sudah kita timpa, lalu mengirim placeholder mentah `{bankwire_bank}` yang
`ps_wirepayment` tak pernah suplai. `uninstall()` tak memulihkan → kerusakan permanen.

### Fakta lintas-versi yang mengikat rancangan

`Mail::getTemplateBasePath()` punya fallback "pindai `modules/*/mails/`" **hanya di 9.1**
(baris 717). Di **1.7.8.11 dan 8.1.6 fallback itu TIDAK ADA** — template wajib ada di
`_PS_ROOT_DIR_/mails/<iso>/`. Jadi menyalin ke `_PS_MAIL_DIR_` **tak bisa dihapus**; yang salah
adalah NAMANYA menabrak milik core. Ini alasan rancangan memakai nama unik, bukan menghapus
penyalinan.

### Perubahan

**1. Nama template jadi milik sendiri.** `mails/<iso>/bankwire.html|txt` →
`mails/<iso>/bankwire_multibank.html|txt` (id + en). Nama itu tak dimiliki core mana pun.

**2. OrderState milik sendiri.** `installOrderState()` berhenti memakai ulang `PS_OS_BANKWIRE`;
pakai kunci sendiri `BANKWIRE_OS_AWAITING`, state baru ber-`module_name = 'bankwire'` dan
`template = 'bankwire_multibank'`.

**3. `copyMailTemplates()` menyalin HANYA `bankwire_multibank.*`.** File core `bankwire.*` tak
pernah disentuh lagi.

**4. `uninstall()` menghapus salinan `bankwire_multibank.*`** dari `_PS_MAIL_DIR_/<iso>/`. Aman
justru karena namanya milik kita.

**5. Titik panggil pindah** ke `BANKWIRE_OS_AWAITING`: `bankwire.php:1138`,
`controllers/front/validation.php:72`, plus komentar `bankwire.php:1073`.

**6. `upgrade/upgrade-1.0.6.php`**: buat state baru + set kunci, salin template baru.
Order historis **TIDAK** dipindah state — mengubah riwayat order lebih berbahaya daripada
manfaatnya, dan restore template core (butir 7) sudah membuat email mereka benar lagi.

**7. Pemulihan file core yang terlanjur tertimpa** — BUTUH KEPUTUSAN BUDI, lihat di bawah.

**8. Bump versi → 1.0.6.**

## fix-orderstate-ownership-root
Status: diterapkan

Revisi disetujui Budi pasca-intervensi cap → `verify_attempts` direset ke 0 (cap membatasi
SATU loop rancang-ulang, bukan seumur hidup module).

**Akar yang dikerjakan:** `ps_configuration` berhenti jadi sumber kebenaran kepemilikan
OrderState. Kolom `ps_order_state.module_name` yang jadi otoritas — tak berdimensi toko
(sama seperti tabelnya), dan tetap benar setelah baris config tersapu atau uninstall gagal
separuh. Baris config turun pangkat jadi **cache** yang selalu boleh dibangun ulang.

### Perubahan

- `findOwnedOrderStates()` — query `ps_order_state WHERE module_name='bankwire' AND deleted=0`,
  urut menaik. Ini satu-satunya penentu kepemilikan.
- `pickCanonicalOrderState()` — saat ada duplikat, yang dipertahankan adalah yang **paling
  banyak dirujuk `ps_orders`**, DIUKUR bukan ditebak (versi lalu memakai "id tertua" dengan
  komentar "paling mungkin dirujuk order" — tebakan yang menelantarkan satu populasi). Seri
  diputus id terkecil. `getValue(..., false)` supaya hitungan penentu ini tak dari cache SQL.
- `migrateOrdersBetweenStates()` — **BARU, dan ini bagian yang selama ini hilang**: konsolidasi
  memindahkan `ps_orders.current_state` DAN `ps_order_history.id_order_state` sebelum duplikat
  dipensiunkan. Tanpa ini order di state non-kanonik tertinggal di status `deleted=1`:
  hilang dari dropdown BO sehingga merchant tak bisa memindahkannya balik, dan
  `hookDisplayPaymentReturn` jatuh ke cabang gagal.
- `syncOrderStateCache()` — satu pemilik penulisan cache; buang semua baris lalu tulis satu
  baris global, jadi baris shop-scoped tak bisa membayangi lagi.
- `getOrderStateId()` — resolver runtime READ-ONLY: baca cache, **validasi** terhadap sumber
  kebenaran (`!deleted`, `module_name` cocok), jatuh ke query bila tak sahih. Sengaja tak
  menulis — jalur checkout bukan tempat memperbaiki state instalasi.
- `retireOrderState()` — mempensiunkan SEMUA state milik module dari sumber kebenaran, bukan
  yang kebetulan ditunjuk satu baris config.
- Titik pakai runtime (`validation.php`, `hookDisplayPaymentReturn`) pindah ke
  `getOrderStateId()`.

### Kelas yang tutup karena seam-nya tak ada lagi

`adv-os-reconciliation-strands-orders-in-retired-state` (migrasi order kini ada),
`adv-os-retire-state-still-reads-single-global-row` (retire baca sumber kebenaran),
dan kelas "state hidup tanpa penunjuk tak terlihat → install membuat state kedua" —
kandidat kini dibangun dari `ps_order_state`, bukan dari penunjuk.

### Ronde verifikasi akar 2 (verify_attempts: 2)

3 error / 7 warning — NAIK dari 1/8. Dua regresi yang KUPERKENALKAN, satu bersifat keamanan.

**`reset()` ternyata KODE MATI.** Aku memverifikasi bahwa `ModuleManager::reset()` memeriksa
