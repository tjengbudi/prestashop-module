# E2E cell contract

Paths relative to `.claude/skills/psm-validate/scripts/` unless they start with `.claude/`. A **cell** is one (version, browser) pair.

Tests that need Docker, flashlight images and Playwright browsers (warm reset, concurrent BO sessions, identical findings, the bankwire success signal) live in `scripts/tests/live/` and skip unless Docker, both browsers, the default-tag flashlight images and the DB image are present locally; they never pass `--allow-image-pull`. They run on a plain (non-git) temp copy of `{project-root}/modules/bankwire`. The identical-findings test and the success signal inject one fault into that copy: `checkout-with-bank.json` step 55 (FO `expect_text` "Please send us your payment by bank transfer") is changed to a text the page never shows, so it fails on every engine (the success signal's one-line patch reverts it), and the identical-findings test requires a non-empty confirmed set. A mismatch in the identical-findings test is rerun once and fails only when it repeats.

## Configured cells

- Configured cells = `psm_target_versions` × `psm_e2e_browsers`, read directly from the `--config` JSON (script defaults `1.7.8,8.1,9.1` and `chromium,firefox` when no config is given). This is the only source of the required set for `ready`. Plan and aggregate keep this set apart from their `--versions`/`--browsers` arguments: the `apply_config_file` mapping (`psm_target_versions` → `versions`, `psm_e2e_browsers` → `browsers`, explicit flag wins) is not used for it. In headless runs the caller's versions and browsers are written into that JSON first (Headless). Test: config 3×2 plus `--versions 9.1 --browsers chromium` still lists the other five cells as rerun.
- One shared normalizer in `ps-flashlight-run.py` (next to `CONFIG_KEY_TO_DEST`, with `SUPPORTED_ENGINES` moved there), used by plan, runner and aggregate: duplicates are dropped; an empty list, a version that is not dotted digits (`\d+(\.\d+)*`), two numerically equal versions (`9.1`, `9.1.0`), or an engine outside `chromium`/`firefox`/`webkit` is an input error (exit 2), replacing `parse_browsers`' silent fallback to the default; a canary or `--cells` version must match a configured string exactly; versions are ordered by numeric dotted comparison (`10.0` is newer than `9.1`), never lexically. History file names use the configured string.
- `--versions`, `--browsers`, `--cells` and the interactive scope menu (SKILL.md On Activation step 2) shape only what a run drives. They never shrink the configured set: the plan applies them as a filter on `e2e_next_cells` (Plan > Run scope). Cells a narrowed run leaves out show in the aggregate's `e2e_cells` without passing gate-grade evidence, so `ready` stays false.
- Gating without E2E stays possible only through `ps-aggregate.py --require` without `e2e`, as today.

## Evidence record (one per cell per run)

- **Storage**: each cell has an append-only history `<reports>/<module>-e2e-<ver>-<browser>.jsonl`, one record per line. After the child exits, ps-run-layer appends one record for every cell it admitted: the child's per-cell result, or, when the child left none, an `inconclusive` record with `reason` `crash`, `stopped` (written from the stop handler before teardown ends), `browser-unavailable` (an engine the binary probe dropped) or `keeper-start` (Warm container); plus the `not-run` and `no-slots` records. A child that reports `status: skipped` (Playwright or Docker absent) or exits 2 leaves no record (Runner > Output). Each append is one `write()` under `LOCK_EX` on the history file, starting with `\n` when the file's last byte is not one (a writer killed mid-line); readers take `LOCK_SH`. A run never rewrites a line, and writing (V, firefox) never touches (V, chromium). A line that does not parse, or whose `started_at` is not UTC ISO-8601, whose `state` is outside the enum, or whose `version`/`browser` is not the file's cell, is corrupt: it is skipped and hides no record before it. While no valid line follows the last corrupt line in the file, the cell gets reason `corrupt-history` and has no passing gate-grade evidence. Test: valid, corrupt, valid lines read as the two valid records.
- **Entry points**: plan and aggregate read E2E evidence only from these histories. Every `ps-run-layer.py --layer e2e` run appends history (`--cells`, or `--versions` = those versions × all configured browsers) and writes no `<module>-e2e*.json` (input errors: Runner). Direct `ps-e2e-run.py` output (SKILL.md Lapis 4, the quickstart TDD loop) keeps the child shape (Producers below) and is never evidence. `ps-aggregate.py --e2e <file>` is an input error (exit 2) naming `--reports-dir`, and the aggregate ignores `<module>-e2e.json` and `<module>-e2e-<ver>.json` even when present, so after the upgrade every cell reads `missing` until re-proved. `--merge-only --layer e2e` takes only `--module`, `--reports-dir` and `--config` (the run input errors and `--session` do not apply) and writes the report view `<module>-e2e.json` = `{module, view: true, cells: {<ver>: {<browser>: <newest record>}}}` for every configured cell, without `validate_layer_shape` or the oldest-mtime rule; nothing reads it as evidence.
- **Newest / latest** within one cell = the last valid line (append order, serialized by `LOCK_EX`), never `started_at`, so a clock step cannot reorder a history; `started_at` only compares records across cells (Plan > Focus cell). Warm (CAP-5) and partial (CAP-4) records sit in the same history as convergence records. They are never gate-grade, so they never stand in for a cold full-scenario record: each rule below picks the newest record that matches it.
- **Fields**: `version`, `browser`, `started_at`, `finished_at` (UTC ISO-8601 with microseconds, this cell's engine start and end), `boot` (`cold`|`warm`), `boot_id`, `session`, `browser_mode` (`parallel`|`sequential`), `scenario_set` (`full`|`partial`), `scenarios_run` (spec `name` list), `source_fingerprint`, `image_tag`, `run_id`, `job_id`, `tier`, `state` (`pass`|`fail`|`inconclusive`|`not-run`), `conclusive`, `reason`, `errors`, `install`, `launch_error`, `bo_authed`, `findings`, `inconclusive`, `authored_assertions`, `scenario_notes`, `browser_notes`, `parallel_only`, `console_errors`, `screenshots`, `scenario_spans` (per scenario `[start, end]` from `time.monotonic_ns()`, emitted by the engine that drove it), `phase_durations`, `boot_phases`, `keeper_boot`, `wall_clock`.
  - A cell whose engine never started (not-run, no-slots, boot or install failure, browser-unavailable, crash) has `started_at` = when ps-run-layer admitted it or decided not to start it, `finished_at` = when the record was written, and `null` for fields no engine produced.
  - `run_id` = RUN_ID of the version process (ps-run-layer's own when no child ran); `job_id` = ps-run-layer's Job ID; `tier` = the new `ps-run-layer.py --tier` (the plan's `e2e_tier`); `boot_id` = RUN_ID of the process that ran bring-up (warm iterations: Phase timings); `session` = the validation session token, minted by `ps-plan-layers.py --new-session` (no module path; any other flag is exit 2; prints only a random `[a-z0-9]{16}`, exit 0) once per psm-validate invocation (interactive: On Activation; headless: per call) and passed as `--session` to every plan call and every `ps-run-layer.py --layer e2e` run; both reject a missing or malformed token (exit 2).
  - `reason` on an `inconclusive` record names the cause: `crash`, `stopped`, `browser-unavailable`, `keeper-start`, `warm-reset`, `no-slots`, `parallel-unconfirmed`, `sequential-reset` or `incomplete-record` when set by those rules, otherwise the first state-rule cause that applies, in this order: `install` (an install result whose `ok` is not true; the runner also copies install failures into `errors`), `launch-error`, `errors` (boot failures before install), `not-driven`. It is `null` on `pass` and `fail`.
  - `errors` and `install` (version level today) and `scenario_notes` (run level today, `ps-e2e-run.py` `main`) are copied into every cell of that boot. The runner emits `browser_notes` keyed by engine; each cell gets only its own engine's notes.
  - Producers: ps-run-layer computes `source_fingerprint` once before admitting any cell and resolves each version's `image_tag` (Config keys > Image tag), and writes `session`, `tier`, `job_id`, `wait-slots` and every record of a cell whose child left no result, with that `image_tag`. The child emits per version `run_id`, `boot`, `boot_id`, `boot_phases`, `image_tag`, `browser_mode` (`sequential` when it drives one browser), `errors`, `install`, `scenario_notes`, and `cells: {<engine>: {...}}` with the remaining per-cell fields; ps-run-layer merges them into one record per cell. Each finding gains `action` and `step` (the action's 0-based index in the spec's `steps` list).
- A `pass` or `fail` record in which any of `session`, `source_fingerprint`, `image_tag`, `boot`, `scenario_set`, `install`, `authored_assertions`, `inconclusive`, `scenario_notes`, `browser_notes` is absent or `null` is read as `inconclusive`, reason `incomplete-record` (today's `authored_assertions=None` rule, generalised).

## State, freshness, gate-grade

- **State** (today's `e2e_layer` rules, applied per cell): `inconclusive` when the engine was not driven, `errors` is non-empty, `install.ok` is not true, or `launch_error` is set; otherwise `fail` when `findings` is non-empty, even if some steps were inconclusive; otherwise `pass`. `conclusive` is true for `pass` and `fail` only. Per-step conclusiveness is unchanged (a BO step other than `goto`/`expect_no_fatal` needs `bo_authed`), so the universal smoke stays conclusive without a BO login.
- **Fresh**: `source_fingerprint` is a SHA-256 over the sorted list of (relative path, size, mtime_ns) for every file under the module directory except `.git/`, the top-level `.psm-*` files and top-level `.memlog.md` (bookkeeping that sibling skills write there and PrestaShop never loads), and `psm_reports_dir` when it lies strictly inside it (a reports dir equal to the module root, or a screenshot dir elsewhere in the module, is an input error, Runner), captured by ps-run-layer before admission. `newest_source_mtime` (Layers 1, 2, 5) keeps `ss.is_skipped` (so `vendor/`, `node_modules/` and deletions still do not stale them) and also skips these bookkeeping files and reports dir, so writing reports stales no layer. Plan, runner and aggregate share one function, `source_fingerprint` in `ps-plan-layers.py` (ps-aggregate loads it as a sibling, ps-run-layer through ps-aggregate): it resolves the module root with `realpath`, then walks with `lstat` and never follows a symlink below it; an entry that vanishes during the walk is left out, and any other stat error is an input error (exit 2) naming the path. `vendor/`, `node_modules/` and `tests/e2e` are included (the install copies the whole directory); `ss.is_skipped` is not used for the fingerprint. A record is fresh when its fingerprint equals the current one and its `image_tag` equals the resolved tag. Adding, deleting or renaming any file changes the fingerprint. File mtime of the record is not used, so a patch that lands during a run leaves that run's records stale. Tests: deleting a file that is not the newest stales every cell; touching a file under `vendor/` stales every cell; editing `.psm-develop-plan.json`, or appending history to a reports dir inside the module, leaves every cell fresh.
- **Full** scenario set: every valid discovered spec plus the universal smoke.
- **Gate-grade**: fresh + conclusive + `boot: cold` + `scenario_set: full`. **Passing gate-grade**: gate-grade + `state: pass` + `inconclusive` empty + `authored_assertions` ≥ 1 + `scenario_notes` empty + `browser_notes` empty. These are today's `inconclusive_note` conditions that drop `ready`, applied per cell. A cell **has passing gate-grade evidence** only when its newest gate-grade record is passing gate-grade: a newer gate-grade `fail` always overrides an older pass. Test: pass then fail on the same fingerprint gives `ready=false` and a step other than `done`.
- E2E part of `ready`: every configured cell has passing gate-grade evidence. The unioned `e2e_browsers` / `e2e_browsers_run` fields are not used for this.

## not-run (CAP-3)

- A cell that fail-fast left unstarted gets a record with `state: not-run`, `conclusive: false`, `reason: "fail-fast after <version>:<browser>"`. A cell not yet admitted, including one waiting in `wait-slots`, is unstarted: fail-fast cancels its wait. The named cell is the one whose `fail` triggered the stop; when that child had several failing engines, it is the first in `psm_e2e_browsers` order. The record is appended to the cell's history and shown in the aggregate's `e2e_cells`. It is never gate-grade and hides no older record. The plan reports reason `not-run` when it is the cell's newest record.
- For a version none of whose cells started, ps-run-layer truncates that version's progress log and writes one `DONE rc=not-run` line with the reason, so no line from an earlier run remains.

## Plan (`ps-plan-layers.py`)

- Reads the configured set as above. Gains `--browsers`, which, like `--versions`, is run scope only (filled from `--config` when absent; explicit flag wins).
- Judges E2E freshness per cell. `rerun_matrix` entries for layer `e2e` cover every configured cell whatever `--versions` (other layers stay limited to `--versions`) and gain `browser` and `reason`. A cell with passing gate-grade evidence gets no entry; otherwise the reason is the first that applies: `corrupt-history` (Evidence record > Storage); `missing` (no record); `stale-tag`, `stale-source` (no fresh record); then by the newest fresh record: `fail`, `not-run`, `inconclusive`, `warm-only`, `partial`, `inconclusive-steps` (gate-grade `pass` with non-empty `inconclusive`), `not-gradeable` (below), `scenario-notes` (gate-grade `pass` whose `scenario_notes` are non-empty and differ from the current `e2e_scenario_notes`), `browser-notes` (any other gate-grade `pass` that is not passing gate-grade). `per_version[ver].layers.e2e`, and `layers.e2e` in canonical mode, become keyed by browser; `rerun` lists `e2e` while any configured cell (per-version mode: of that version) has an e2e `rerun_matrix` entry. Tier fields and `phase1_reuse` are emitted in both modes. `all_reuse` keeps today's computation over these `rerun` lists and is informational only: the gates are `phase1_reuse` and `e2e_step`.
- Owns tier order and emits `e2e_tier` (0 for `focus`, `cold-version`, `cold-canary`; 1 for `gate`; for `blocked-by-scope`, the tier of the blocked step; `null` for `done`, `blocked-not-gradeable` and `blocked-infra`), `e2e_step`, `e2e_focus_cell`, `e2e_next_cells` (the cells the next run drives), `e2e_required_cells` (the step's cells before the scope filter; for `blocked-not-gradeable` and `blocked-infra` the cells in `e2e_blocked_causes`; empty for `done`), both lists of `"<ver>:<browser>"` in numeric version order then `psm_e2e_browsers` order, `e2e_cells_arg` (`e2e_next_cells` grouped as the `--cells` value), `e2e_blocked_causes` (`{"<ver>:<browser>": cause}` for a `blocked-*` step; `out-of-scope` for each cell the run scope removed), `e2e_scenarios` (`failed-only`|`full`), `e2e_warm` (true only for a `focus` step whose focus cell has a recorded failure, does not diverge (step 7), and has no record with reason `warm-reset` or `keeper-start` in the current `--session`; the orchestrator uses the warm container only when it is true and the run is interactive), `source_fingerprint` (current) and, per version, `phase1_reuse` and `clean` (Phase 1). The orchestrator runs exactly `e2e_next_cells` and never picks a tier by judgment.
- Derivation uses the records of configured cells only. A cell is **failing** when its newest cold, full-scenario, conclusive record (fresh or stale) has `state: fail`. **Focus cell** = among failing cells, those whose failing record belongs to the newest run (a run = the records sharing a `job_id`; the newest run holds the failing record with the highest `started_at`); ties inside that run: numeric version order, oldest first, then `psm_e2e_browsers` order. No failing cell → the canary. Test: two failing cells from one tier-1 run walk through both loop-backs. A cell has a **recorded failure** when its newest conclusive record of any boot, scenario set, or freshness has `state: fail`. A cell is **not-gradeable** when its newest gate-grade record is a `pass` with empty `inconclusive` whose `authored_assertions` is 0, or whose `scenario_notes` is non-empty and equals the plan's current `e2e_scenario_notes` (git-derived notes, such as an uncommitted spec deletion, change without changing the fingerprint). In steps 4 to 7 a not-gradeable cell counts as having passing gate-grade evidence; it never counts for `done` or `ready`. Steps, first match wins (`tier-matrix.md` > Loop-back):
  1. `done`: every configured cell has passing gate-grade evidence. `e2e_next_cells` is empty.
  2. `blocked-not-gradeable`: every configured cell has passing gate-grade evidence or is not-gradeable, and some cell is not-gradeable. Nothing runs; `e2e_blocked_causes` names the not-gradeable cells. So a smoke-only module (no authored scenarios), or one whose specs carry notes, still runs tier 1 once after the canary, every configured cell gets the universal smoke, results are reported, and `ready` stays false. Test: a smoke-only module derives `gate` with the five non-canary cells after the canary run, then `blocked-not-gradeable`.
  3. `blocked-infra`: some configured cell's two newest records, not counting records with reason `stopped`, both carry the current `--session`, are fresh with the same `source_fingerprint`, and each has an infra cause, the same cause or not. A `stopped` record is an operator stop, not an infra result: it is skipped, so it neither counts toward the two nor breaks them. A record's infra cause, whatever its boot or scenario set: an `inconclusive` record → its `reason`; a `pass` with non-empty `inconclusive` → `inconclusive-steps`; any other `pass` with non-empty `browser_notes` → `browser-notes`; any other record (`fail`, a `pass` without either, `not-run`) has none, so it breaks the two. Nothing runs; `e2e_blocked_causes` names the cells. The E2E loop then stays ended for the session even after a later patch (E2E loop ended); only a new validation session retries. Test, all in one session on one fingerprint: `no-slots`, `no-slots` give `blocked-infra`; `no-slots`, `crash` give `blocked-infra`; `no-slots`, `stopped`, `crash` give `blocked-infra`; `no-slots`, a `pass` with no inconclusive steps or browser notes, `crash` do not.
  4. `gate`: the canary has passing gate-grade evidence and no cell is failing → tier 1 cells.
  5. `cold-version`: the focus cell is not the canary and its newest fresh conclusive record is a `pass` → V = focus version with all configured browsers, cold, full, one boot.
  6. `cold-canary`: no non-canary cell is failing, the canary lacks passing gate-grade evidence, and either its newest fresh conclusive record is a `pass`, or it has no fresh conclusive record and its newest cold full conclusive record is a stale `pass` → the canary cell, cold, full. Test (steps 5 and 6): fail then pass on one fingerprint promotes; pass then fail does not.
  7. `focus`: otherwise → the focus cell only. The focus cell **diverges** when a warm or partial `pass` on the current fingerprint is newer than a cold full `fail` on it (residue or order the warm reset or subset hides). Without a recorded failure, or when it diverges: cold, `full` (on a clean module the first canary run is gate-grade, so the next derivation is `gate`). Test: cold fail, warm pass, cold fail on one fingerprint derives a cold full `focus`. Otherwise: `e2e_warm` as above, and `e2e_scenarios` is `failed-only` when the focus cell's latest full-scenario record has a non-empty failed set (see Failed-only rerun), else `full`. All other steps are `full`.
- **Run scope**: after the step is derived, `e2e_next_cells` keeps only the cells inside `--versions` × `--browsers`; `e2e_required_cells` keeps the unfiltered list. When the step is not `done`, `blocked-not-gradeable` or `blocked-infra` and the filter leaves `e2e_next_cells` empty, `e2e_step` becomes `blocked-by-scope` and nothing runs.
- **Phase 1**: `phase1_reuse` is true when no layer other than `e2e` and `adversarial` reruns for the plan's `--versions`; every call that reads it uses `--per-version` (canonical files are written only in Phase 2). `per_version[V].clean` is true when `phase1_reuse` is true for V and none of V's per-version Layer 1, 2 and 5 files holds a blocking finding, judged by ps-aggregate's layer functions (loaded lazily, since ps-aggregate loads ps-plan-layers at import). The orchestrator judges version V **clean** from that field, overridden by state it keeps for the session in two cases: a Layer 2 or 5 run of V that reported `skipped` (Docker absent) counts as clean, and in headless (which patches nothing) V is clean once its loop has run its stale layers once, whatever their findings. Every rule below that says clean, the Phase 2 entry check included, uses this judgment. A version's Phase 1 loop (`--versions V --per-version`; its E2E fields are not read) ends when V is clean. Phase 1 loops run only for the run scope's versions. The **hosting version** is the version of `e2e_focus_cell` when the orchestrator enters Phase 1 (session start or loop-back), so the canary's unless a cell is failing; when that version is outside the run scope, it is the first in-scope version (whose E2E plan call then reports `blocked-by-scope` for a step it cannot run). Its loop runs first and hosts every tier-0 step until it ends, even when the focus cell moves to another version; in each iteration it runs the E2E step only once V is clean, taking it from a separate plan call whose `--versions`/`--browsers` are the operator's run scope (default all configured), never the loop's V, and running exactly its `e2e_next_cells`. It ends only when V is clean and `e2e_step` is `gate` or `done` or the E2E loop has ended. Test: a loop-back hosted in 8.1 derives `cold-canary` with `e2e_next_cells` = [9.1:chromium], not `blocked-by-scope`.
- **Phase 2 entry**: after the last loop ends, one `--per-version` plan call with the run scope must show every version clean and `e2e_step` `gate` or `done`, unless the E2E loop has ended or convergence was stopped (below). Otherwise the loops of the dirty versions, and the hosting loop for a tier-0 step, run again. So a patch made in any loop reopens every version whose Layers 1, 2, 5 or canary evidence it staled.
- **Phase 2**: spawn the Layer 3 lenses (unless the plan reuses Layer 3), then loop: run `e2e_next_cells`, re-plan, repeat while `e2e_step` is `gate`; a tier-0 step is a loop-back and re-enters Phase 1 (`tier-matrix.md` > Rules); `done` or E2E loop ended leaves the loop. Then the **wrap-up**, which boots nothing: merge Layer 3, then `visual-pending` (`tier-matrix.md` > Visual review); `ps-run-layer.py --merge-only` for Layers 2 and 5 (always, no `all_reuse` gate) and for `e2e` (report view); the cross-version static scan; `ps-aggregate.py`.
- **E2E loop ended**: a run whose output says `skipped` (Runner > Output), a `blocked-*` step, `psm_e2e_enabled` false (an orchestrator gate), or gating by `--require` without `e2e`. The orchestrator keeps that state for the session, reports it (for `blocked-*`, naming `e2e_required_cells`), and never repeats the step; it is never a pass, and `ready` stays false unless `--require` excludes `e2e` (Configured cells). The hosting loop stops waiting for `gate`/`done`, and Phase 2 runs its other layers.
- **Stop convergence** (operator action): for Layer 1, 2 or 5 findings, or a canary (focus-cell) E2E failure, that will not be fixed this session. Interactive: in every Phase 1 iteration where V is not clean or the focus cell has a recorded failure, the orchestrator offers Budi "stop convergence" next to patching; it runs only when he chooses it. Choosing it ends the E2E loop (above) and every Phase 1 loop at once, skips the Phase 2 entry check, and runs no further E2E step, so the post-canary tier (tier 1) does not run. The orchestrator stops its keepers, spawns the Layer 3 lenses, then runs the Phase 2 wrap-up (above). The verdict is `ready: false` whatever the aggregate computes. The report says convergence was stopped by the operator at `e2e_step` `<step>` (tier `<e2e_tier>`) of the last plan call, lists the open Layer 1, 2 and 5 findings per version and the failing E2E cells, and names every configured cell without passing gate-grade evidence as not proven. Headless has no operator prompt: its stop at the first E2E step that is not clean (Headless) is the equivalent and runs the same wrap-up.

## Runner (`ps-run-layer.py`, `ps-e2e-run.py`)

- `ps-run-layer.py --cells <ver>:<browser>[+<browser>],...` gives each version its own browser list in one invocation (one Job ID, one cap). The orchestrator passes `e2e_next_cells` here and the plan's `e2e_tier` as `--tier`.
- **Child flags**, new on `ps-e2e-run.py` and set only by ps-run-layer: `--engines <list>` (the version's engines; outside `CONFIG_KEY_TO_DEST`, overrides `--browsers` and `--config`); `--run-id <hex12>` (the slot claim's pre-generated RUN_ID, Config keys; assigned to `fl.RUN_ID` before `job_register` or any label or progress use; engine workers inherit the version process's); `--slot-cost <n>` (the admitted cost, stamped verbatim as `psm.slots` even when the binary probe later drops an engine; a keeper gets 1; when absent, as in a direct run, the child stamps the number of engines it drives in parallel (Parallel browsers), or 1 when it drives one engine or runs with `--sequential-browsers`); `--progress-append` (Phase timings).
- **Input errors** (exit 2): `--cells` with another layer; and for layer `e2e`: neither or both of `--cells` and `--versions`; a `--tier` missing or other than `0` or `1`; a version repeated in `--cells`; a cell outside the configured set; `--warm` or `--scenarios-from-failed` with other than exactly one cell; `--per-version` or `--jobs`; `psm_reports_dir` equal to the module root; a passthrough `--screenshot-dir` inside the module but outside `psm_reports_dir`. `RESERVED_PASSTHROUGH` (prefix abbreviations included) gains every flag ps-run-layer sets on a child: `--browsers`, `--engines`, `--run-id`, `--slot-cost`, `--progress-append`, `--sequential-browsers`, `--scenarios`, `--use-warm`, `--keep-warm`, `--warm-owner`, `--warm-ttl`, `--engine-worker`, `--config`.
- `ps-e2e-run.py` exit codes: 0 every driven cell passes, or E2E is skipped (Playwright/Docker absent, unchanged); 3 at least one cell has `state: fail`, whatever the other engine's state; 1 otherwise (infra failure or inconclusive cell); 2 input error. ps-run-layer and the tests that read exit 1 as "version failed" treat 3 the same way. `ps-run-layer.py --layer e2e` exits the same way over all records it appended: 3 when any is `fail`, else 1 when any is inconclusive, `not-run` or `no-slots`, else 0; 143 when stopped via `--stop-job`, as today.
- **Output**: `ps-run-layer.py --layer e2e` ends by printing one JSON line on stdout, `{"e2e_status": "ran"|"skipped", "reason", "appended": ["<ver>:<browser>", ...], "source_fingerprint"}`. It reports `skipped` and exits 0 when `docker_available()` is false before slot counting (nothing appended) or when any child reported `status: skipped` and no appended record is `fail` (other children's records are still appended), so the E2E loop ends instead of re-deriving the skipped cells; an appended `fail` wins (`ran`, exit 3). A child exit 2 stops queued cells as fail-fast does (`not-run`, reason `input-error after <ver>`), in-flight children finish, and ps-run-layer exits 2.
- `ps-e2e-run.py --scenarios <name,...>` is a seed: the child adds prerequisites (Failed-only rerun) and the universal smoke, checks the names against `discover_scenarios`, and on a fallback (Failed-only rerun) runs the full set, logs why in its progress log and records `scenario_set: full`.
- Fail-fast: ps-run-layer queues cells under the cap. On the first reaped child, in completion order, that appended a `fail` record, it starts no further queued cell; an exit-3 child whose output crashed has no conclusive finding and does not trigger fail-fast. In-flight children finish. Exit 1 does not trigger fail-fast. Inside one engine all scenarios run, and the other engines of a CAP-7 version, already running, finish. In the sequential fallback (Parallel browsers) the version process applies the same rule: after the first engine's `fail`, it starts no further engine, and each gets `not-run`.

## Warm container (CAP-5)

- Interactive runs only. A headless run never passes `--warm`, `--keep-warm` or `--use-warm`.
- **Chain**: when `e2e_warm` is true, the orchestrator calls `ps-run-layer.py --cells V:b --warm --session <token>`. ps-run-layer's owner token, warm run or not (Teardown), is always its `--session` (Evidence record > `session`); it passes it to the keeper as `--warm-owner`. ps-run-layer finds this owner's live keeper for (module path, V) or starts one, admitted like a cold boot (cost 1, `wait-slots`, `no-slots`): it generates the warm Job ID (`make_job_id(<module>, "e2e-warm")`, i.e. `<module>-e2e-warm-<HHMM>-<hex>`), prints and logs it, writes `<tmp>/psm-warm/<warm-id>/starting` (owner token, module path, version, keeper PID), and spawns `ps-e2e-run.py <module path> --versions V --keep-warm --job-id <warm-id> --run-id <claim RUN_ID> --slot-cost 1 --progress-file <reports>/<warm-id>.progress.log --warm-ttl <psm_e2e_warm_ttl> --warm-owner <token> -o <tmp>/psm-warm/<warm-id>.result.json` with `start_new_session`; the keeper never forks (Owner). Keeper and iteration both get ps-run-layer's passthrough and `--config`. ps-run-layer then waits for `session.json` in phase `keeper-wait`, until the keeper exits (its pull, bring-up, wait-healthy and `baseline` timeouts bound this; `baseline` uses `--timeout`); a lookup that finds a live keeper's `starting` file waits the same way and never starts a second keeper. A keeper that exits first gives the cell an `inconclusive` record, reason `keeper-start`, with `errors` and `boot_phases` from its `-o` result, `<tmp>/psm-warm/<warm-id>.result.json`, which the keeper writes on every exit path before `session.json` exists and ps-run-layer deletes after reading. A ps-run-layer stopped during the wait stops that keeper with `--stop-job <warm-id>`, and the cell gets `stopped`. Then ps-run-layer attaches (below) and runs the child with `--use-warm <warm-id>`. The keeper boots, captures the baseline, holds and tears down the container; the iteration process runs reset, install and the browsers.
- **Owner**: the keeper is registered (`job_register`) under its own warm Job ID. It runs bring-up itself, so the container carries the keeper's PID as `psm.owner-pid`: `--cleanup-orphans` sees a live owner and leaves it, and reaps it only after the keeper is dead. `--stop-job <warm-id>` signals the keeper, which tears the container down. `cleanup_decision` is unchanged. After `wait-healthy` the keeper captures the baseline (below) and writes `<tmp>/psm-warm/<warm-id>/session.json` (outside `<tmp>/psm-jobs/`, whose `*.json` are process entries): owner token, keeper PID, orchestrator mode and `PS_DOMAIN` both as requested (before `auto` resolves or the port floats) and as resolved, published port, DB image, admin path, container, DB and network names, compose file and project, module path, version, image tag, progress-log path, its `boot_id` and `boot_phases`. It deletes that directory at teardown. It logs to `<reports>/<warm-id>.progress.log` (keyed by warm Job ID, since keepers of different owners may coexist), with an `ALIVE idle` line (remaining TTL) every heartbeat while idle, so the stall rule never flags it. `--list-jobs` adds `owner` and `module` from `session.json` to warm entries; the On Activation report uses it to list live keepers of other owner tokens for the module with their `--stop-job` command; stopping one needs Budi's OK, as for any foreign job.
- At most one keeper per (module path, version, owner token); module path is its `realpath` wherever it identifies a keeper (`starting`, `session.json`, lookup, pre-iteration check). ps-run-layer looks up only this owner's keeper: a live keeper of another owner token (including one left by an earlier psm-validate invocation) does not stop it from starting this owner's keeper (one more slot), and is never attached, reset, reused or stopped. **Cold-boot fallback** (here and below): a one-shot cold run of the cell without a keeper, admitted by ps-run-layer like any cold cell; its record has `boot: cold` and is gate-grade only when also `full`.
- **Attach**: ps-run-layer resolves the warm-id itself (lookup in `<tmp>/psm-warm/` by module path, version and owner token), takes the exclusive lease (non-blocking `flock` on `<tmp>/psm-warm/<warm-id>/lease`) for the iteration, then checks that `session.json` still exists, runs the pre-iteration check, and holds the lease until the child exits; when the lease is held, the iteration cold-boots and logs the reason. It prints and logs both its own Job ID and the warm Job ID. Its CAP-5 assertions read its own progress log. The iteration that started the keeper carries its boot as `keeper_boot` (Phase timings).
- **Idle TTL**: idle time counts from writing `session.json`, then from the last lease release. After `psm_e2e_warm_ttl` (default 60 minutes) idle, the keeper takes the lease itself (non-blocking; held → keep waiting), holds it until it has deleted its session directory, then tears down and exits. `--stop-job` (SIGTERM) tears down at once, lease or not; an iteration whose container goes away mid-run gets `inconclusive`, reason `stopped`.
- **Pre-iteration check** (ps-run-layer, under the lease): the keeper PID is alive (registry `entry_state`), the container is running and healthy, its image tag equals the resolved tag, its requested orchestrator mode, requested `PS_DOMAIN`, DB image and admin path in `session.json` equal the current passthrough or config values, and its module path and version match the requested cell. A dead keeper: ps-run-layer deletes its session directory, leaves the container to `--cleanup-orphans`, and the iteration cold-boots and logs `keeper-dead`. Any other mismatch: ps-run-layer stops this owner's keeper via `--stop-job`, and the iteration cold-boots and logs the reason.
- **Reset per iteration**: the keeper captures the baseline once, after `wait-healthy` and before the first install: phase `baseline`: a `--databases` dump through `ps-scenario-run.py`'s `DB_PRELUDE` (loaded with `load_sibling`), so loading it recreates the database with its charset, and the docroot file list. Each iteration runs `reset-db` (drop the database, then load the dump; a plain `mysql < dump` keeps tables created after the dump, such as the module's own), `reset-files` (always delete `modules/<mod>`, then every docroot file and directory absent from the baseline list, which covers overrides, theme module templates, uploads and translations, then the contents of `var/cache`, including `class_index`, keeping the directory), and `reset-opcache` (reload the web tier, detected at runtime: `kill -USR2` on the php-fpm master when `/proc/*/comm` names a `php-fpm` process, else `apachectl -k graceful` when present, else the reset fails; the live warm-reset test runs on the three default tags; a CLI `opcache_reset()` does not reach the web server), then runs `install`, `wait-http` and `warmup-bo` as a cold boot does. Files that existed at baseline and were modified are not restored; the cold runs catch that residue. A failed reset or reload gives the cell `inconclusive`, reason `warm-reset` (the failing sub-phase in `errors`); ps-run-layer stops the keeper, and `e2e_warm` stays false for the rest of the session (Plan), so the next run boots cold.
- **Teardown**: ps-run-layer stops this owner's live keepers for the module via `--stop-job` (which returns once the container is removed) before counting slots for any `--layer e2e` run without `--warm` (`cold-version`, `cold-canary`, `gate`, or a cold `focus` run) and for a `--warm` run for another version (the focus cell changed). Layer 2 and 5 runs never stop a keeper. The orchestrator stops its keepers with `--stop-job` when the hosting loop ends and at session end, including after the E2E loop ended.
- **Test**: a file deleted from source, a row in a core table, and a row in a table the module created, all written in iteration N, are absent in iteration N+1, and a changed PHP constant is visible over HTTP in iteration N+1.

## Failed-only rerun (CAP-4)

- Flag: `--scenarios-from-failed` on `ps-run-layer.py`, set when the plan emits `e2e_scenarios: failed-only`. ps-run-layer resolves the failed set from the cell's history and passes it to the child as `ps-e2e-run.py --scenarios <name,...>`.
- The failed set is per cell and comes from that cell's latest full-scenario record (cold or warm, fresh or stale): the union of `findings[].scenario` and `inconclusive[].scenario`. The rerun drives the failed set plus its prerequisites plus the universal smoke, with the same engine. Prerequisites of a spec are its transitive `requires` (Scenario prerequisites); a failed spec whose `requires` field is absent instead pulls in every valid spec whose file name sorts before it, plus their own prerequisites. An explicit `"requires": []` declares none.
- No full record, an empty set, or a name that no longer matches a spec → run the full set and log why. `psm-universal-smoke` is exempt from the name check, because it always runs.
- The record gets the `scenarios_run` list and `scenario_set: partial`, or `full` when the driven set equals the full set.

## Scenario prerequisites (`requires`)

- New optional scenario spec field `requires`: a list of scenario names (the spec's `name`, or its file stem when `name` is absent). The implementation adds `requires` to bankwire's specs in `{project-root}/modules/bankwire/tests/e2e/*.json` (the live-test fixture): `checkout-with-bank.json` (name `bankwire-checkout-with-bank`) declares `"requires": ["bankwire-bo-activate-indonesia", "bankwire-bo-allow-indonesia-payment", "bankwire-checkout-empty-banks-safe"]`, the `name`s of `bo-setup-country.json`, `bo-setup-payment-country.json` and `checkout-empty-banks.json`, `bo-setup-payment-country.json` declares `["bankwire-bo-activate-indonesia"]`, and `admin-config-reachable.json`, `bo-setup-country.json` and `checkout-empty-banks.json` declare `[]`.
- Validated in `ps-e2e-run.py` `discover_scenarios`, the single owner of spec validity, so `ps-plan-layers.py` reports problems in `e2e_scenario_notes` before any boot. First, every spec whose effective name equals another spec's, or `psm-universal-smoke`, is skipped with a note naming all files that share it. Then, like other invalid specs, a spec is skipped with a note when `requires` is not a list of strings, names a spec that does not exist, names itself, or is part of a cycle (every spec in the cycle is skipped, and the note names the cycle). A spec whose prerequisite is skipped is skipped too. `psm-universal-smoke` is a valid name in `requires` and a no-op, since the smoke always runs first.
- Run order: universal smoke first, then a stable topological sort over `requires` that always takes the ready spec with the smallest file name (Kahn's algorithm); test: a dependent whose file name sorts before its prerequisite runs after it. `requires` changes only selection and order: a dependent whose prerequisite failed still runs and is judged as today.

## Parallel browsers (CAP-7)

- The version process (`ps-e2e-run.py`) spawns one `ps-e2e-run.py --engine-worker` subprocess per engine against the one booted container (sync Playwright stays alone in its process). Workers are registered under the same Job ID, so `--stop-job` reaches them. The version process owns teardown, forwards SIGTERM, and reads each worker's result from its output file; a worker that exits without a parseable result gives its cell `inconclusive`, reason `crash`, with the exit code in `browser_notes`. Each worker has its own `ctx` copy (including `bo_authed`), its own screenshot subdir `<shots>/<ver>/<engine>`, and appends to the version's progress log with lines tagged `browser:<engine>`. Only the version process calls `progress_init` and writes `DONE`; workers never write `DONE`.
- **Cross-engine lock** (exclusive for BO): every scenario holds `fcntl.flock` on `<tmp>/psm-locks/<job>-<ver>.bo.lock` for its whole run and releases it before the engine's next scenario. A scenario with a BO step (any `goto` with `area: "bo"`, the `_needs_bo` test applied per scenario) takes it exclusive (`LOCK_EX`); an FO-only scenario takes it shared (`LOCK_SH`). So while any engine runs a BO scenario, no scenario of any kind runs on another engine, and FO-only scenarios run in parallel only with other FO-only scenarios; a BO scenario can never overlap, and so never mask, another engine's scenario. The OS releases it when the holder exits; the version process deletes the file after all workers exit. `_bo_login` runs outside the lock: concurrent same-admin logins are what the next test proves. The universal smoke has a BO step, so it takes the lock exclusive. Waiting is logged as phase `lock-wait:<engine>`. The wait has no timeout of its own: it lasts while the other engines' holding scenarios run, which their step timeouts and finite scenario lists bound. Test: on bankwire with two engines, no `scenario_spans` entry of a BO scenario overlaps an entry of the other engine.
- **Lockstep**: in parallel mode the engines advance scenario by scenario. The steps are the engines' scenario lists merged in Run order (Scenarios); with the full set, which every gate-grade run uses, every engine runs the same list, so step k is the same spec on every engine. An engine starts step k+1 only after every engine has finished step k (any outcome), so a change one engine's scenario makes to shared shop state (for example a bank added by a checkout scenario) cannot reach another engine before that engine has run every earlier step. The cross-engine lock still applies inside a step: a BO step's scenario runs on one engine at a time, an FO-only one on every engine at once. Mechanism: after step k (or at once when it does not run step k's spec) the worker creates `<tmp>/psm-locks/<job>-<ver>.step/<engine>.<k>`, then waits until that file exists for every other engine; when the version process reaps a worker it creates `<engine>.done`, which counts as every step done, so the barrier never waits on an exited worker. Waiting is logged as phase `barrier-wait:<engine>`, with no timeout of its own, like `lock-wait`. The version process deletes the directory after all workers exit. Sequential passes (BO-login fallback, `rerun-seq`) and the sequential fallback (Slots) drive one engine alone and use no barrier. A browser phase therefore lasts roughly the sum over steps of the slower engine's time for FO-only scenarios and of every engine's time for BO scenarios. Test (live): on bankwire with two engines, every engine's `scenario_spans` entry of step k+1 starts after every engine's entry of step k ends.
- A live test proves that two concurrent BO sessions with the same admin work on every target version: engine A logs in, then engine B, then each loads `AdminModules` and is still authed (today's `_bo_login` check: the URL is not `controller=AdminLogin`); a failing tag fails the test. At runtime, when an engine's BO login fails while another's succeeded, the version process discards that engine's first-pass result and runs it again alone as its sequential pass (`browser:<engine>#2`, below); only that pass counts, its findings need no sequential confirmation, and the record keeps `browser_mode: parallel`. When every engine's login fails, or the second login fails too, BO steps stay inconclusive as today and no further BO-login fallback pass runs; the `rerun-seq` pass of Parallel-only failures still runs for every engine that needs one. The fallback is logged.
- **Parallel-only failures**: a failure seen in parallel mode counts only when it reproduces sequentially. A version process that drives several browsers in parallel captures a snapshot right after `warmup-bo` (phase `snapshot-db`): a DB dump made as Warm container `baseline` does, plus the docroot file list. After all workers finish and before teardown, the version process takes the engines in `psm_e2e_browsers` order and gives each at most one sequential pass, alone against the same container with its full scenario set: the BO-login fallback pass above, or else a rerun (phase `rerun-seq:<engine>`) when it has findings or when any engine's parallel pass has a finding in a scenario this engine also drove in parallel; one rerun covers its full scenario set, so an engine never gets a second sequential pass. Each pass starts with a full reset to the snapshot, as Warm container's reset does: `reset-db` (drop, then load the dump), `reset-files` (as there, against the snapshot list, then a fresh copy of the module source to the emptied `modules/<mod>` without install, since the restored DB already holds the installed state) and `reset-opcache`, then `wait-http` and `warmup-bo`; these phases go into `boot_phases` (Phase timings, suffixed `#2`, `#3`). As with the warm reset, docroot files that existed at the snapshot and were modified are not restored. `{browser}` expands to `<engine>-seq` and screenshots go to `<shots>/<ver>/<engine>-seq`, so the pass's data and images do not collide with the first pass; the record's `screenshots` are that pass's. The cell's `findings` become the rerun's findings (for an engine rerun only because of another engine's finding, that is every rerun failure): the parallel findings whose (scenario, step, action) also fails in the rerun, plus every rerun failure the parallel pass did not report. Each is a blocking finding like any other, so the cell is `fail`; a rerun failure is never moved to `inconclusive` and is never an infra cause (Plan step 3). Parallel findings the rerun does not reproduce move to `parallel_only`, which never changes `state` or gate-grade and is shown in the aggregate's `e2e_cells`. Inconclusive steps of the rerun are added to `inconclusive`. The record keeps `browser_mode: parallel` and `scenario_set: full`. When the container is no longer up and healthy for the rerun, or the snapshot or any reset phase failed, the cell gets `state: inconclusive`, `reason: parallel-unconfirmed`, with the unconfirmed findings in `parallel_only`. ps-run-layer admits a version with `--sequential-browsers` while any configured cell of it has a newest record with reason `parallel-unconfirmed`. The child's exit code and fail-fast see only the confirmed result.
- **Slots**: ps-run-layer is the only slot owner. It admits a version that drives n browsers at cost n when n slots are free, otherwise at cost 1 with `--sequential-browsers` passed to the child, which then drives its browsers one after another in `psm_e2e_browsers` order and logs the fallback. In that fallback, when the version drives more than one browser, the version process also captures the snapshot right after `warmup-bo` (phase `snapshot-db`, as in Parallel-only failures), and before each engine after the first runs the same full reset a sequential pass starts with (`reset-db`, `reset-files` with a fresh module copy and no install, `reset-opcache`, then `wait-http` and `warmup-bo`, in `boot_phases` suffixed `#2`, `#3`), so every engine that runs starts from the state the parallel mode starts from. Each engine already runs alone, so its findings need no confirmation pass and stand as its cell's findings. When the snapshot or a reset phase fails, or the container is no longer up and healthy before an engine, every engine not yet driven gets `state: inconclusive`, reason `sequential-reset`, with the failing sub-phase in `errors`. Fail-fast still applies (Runner): after an engine's `fail`, no further engine starts and no reset runs for it. The mode never changes mid-run and is recorded as `browser_mode`.
- **Identical findings** (CAP-7 success): on bankwire, for each version V of a parallel run (`--cells V:chromium+firefox` with enough free slots), the set of (version, browser, scenario, step, action) tuples of `findings`, after its sequential confirmation, equals the union of the sets from the baseline: one cold run per engine, each its own `ps-run-layer.py --layer e2e` invocation on the same module and source, first `--cells V:chromium`, then `--cells V:firefox`. Each baseline run drives one engine, so fail-fast in one cannot leave the other `not-run`.

## Phase timings (CAP-6)

- Measured by in-process timers (the progress log is truncated every run). Every phase that emits `START`/`END` is recorded. Each entry is `{seconds, outcome}`.
- Container phases (`pull`, `bring-up`, `wait-healthy`, `install`, `wait-http`, `warmup-bo`, `snapshot-db`, `teardown`, the warm `baseline`, and `reset-db`, `reset-files`, `reset-opcache` of a warm iteration, a sequential pass or the sequential fallback) go into `boot_phases` with the boot's own `wall_clock`, identified by `boot_id`. The same `boot_phases` object is copied into each cell of that boot. A warm iteration's reset, `install`, `wait-http` and `warmup-bo` phases form its record's boot (`boot_id` `<keeper boot_id>#<iteration RUN_ID>`); the keeper's own phases stay under the keeper's `boot_id`, carried once, by the iteration that started the keeper, as `keeper_boot` = `{boot_id, boot_phases, wall_clock}`. `phase_durations` holds only the cell's `wait-slots`, `keeper-wait`, `browser:<engine>`, `lock-wait:<engine>`, `barrier-wait:<engine>` and `rerun-seq:<engine>`. The cell's `wall_clock` is `finished_at` minus `started_at`.
- `wait-slots` runs in ps-run-layer before the child starts. ps-run-layer truncates the version's progress log before it and writes its lines through a progress helper that takes the path and version per call; a child started by ps-run-layer gets `--progress-append` and does not truncate it again. The wait phases `wait-slots`, `keeper-wait`, `lock-wait:<engine>` and `barrier-wait:<engine>` emit `ALIVE` lines naming what they wait for (counted containers, the keeper's log, the holding engine, the engines not yet done with the step) and never `SLOW` (`PROGRESS_SLOW_AFTER_PHASE` exempts them): they last as long as the phases they wait on, which carry their own bounds.
- A phase that did not occur is omitted, not 0. A phase that occurs more than once in one boot or cell (manual-mode `wait-healthy` for the DB, then for PS; `lock-wait:<engine>` and `barrier-wait:<engine>` per scenario that waits; a second `browser:<engine>` after the BO login fallback) gets the suffix `#2`, `#3`, and so on. Nested phases are not subtracted, and parallel browser phases overlap.
- The aggregate surfaces `e2e_phase_durations[ver] = {boots: {<boot_id>: {phases, wall_clock}}, browsers: {<engine>: {phases, wall_clock}}}` (`phases` = the boot's `boot_phases` or the cell's `phase_durations`) from the records it actually used for the verdict, counting each `boot_id` (`keeper_boot` included) once.

## Aggregate (`ps-aggregate.py`)

- Reads the configured set from its new `--config` flag (script defaults when absent); its versions are the target versions of every layer, replacing `--versions` and the static payload's versions (a `--versions` that differs is an input error, exit 2). A configured version missing from a layer's results (a narrowed run, e.g. Layer 1 scanned only 9.1) is unproven for that layer, never an input error: that layer's entry for the version is not conclusive and carries its `reason`, `versions[ver].ready` and `ready` are false, and the report names the version and layer as not proven. Implementation change in `ps-aggregate.py` `main`: the gate that exits 2 when a target version is absent from the static-scan result (`unscanned`) is removed; `static_layer` already returns `conclusive: false` for such a version, which drops `ready` through `version_ready`. The empty-target gate stays (the normalizer rejects an empty configured list, Configured cells). Reads the cell histories from `--reports-dir`, resolves tags as plan and runner do through its new `--tag-map` and `--extra-tag-map` (Config keys > Image tag), takes an optional `--session` (a configured version none of whose cells has a record of that session, and some of whose cells lack passing gate-grade evidence, gets `versions[ver].reached: false`), and reuses the plan's per-cell state and freshness functions.
- Per cell it selects one record: the newest gate-grade record, else the newest record. Emits `e2e_cells` = `{ver: {browser: {state, gate_grade, reason, findings, parallel_only}}}` and, when `--require` includes `e2e`, drops `ready` when any configured cell lacks passing gate-grade evidence. Every other E2E field (`pass` and its findings, `versions[ver].layers.e2e`, `conclusive`, `inconclusive_note`, `versions[ver].ready`, `e2e_conclusive`, `e2e_smoke_only`, `e2e_scenario_notes`, `e2e_phase_durations`) comes from the selected records only: `versions[ver].layers.e2e.conclusive` is true when every configured cell of V has a conclusive selected record, and its `inconclusive_note` names V's cells lacking passing gate-grade evidence with their reasons; `e2e_conclusive` is the AND over configured versions; `e2e_smoke_only` is true when some selected record is `pass`/`fail` and every such record has `authored_assertions` 0. Per version, the E2E layer (`versions[ver].layers.e2e`, plus new `versions[ver].e2e_state` and `versions[ver].reason`) is `fail` when some configured cell's newest gate-grade record is `fail`; otherwise `inconclusive` when any configured cell lacks passing gate-grade evidence (reason as in the plan, except `stale-fail` in place of `stale-source`/`stale-tag` when the cell is failing (Plan)); otherwise `pass`. Findings of a selected record that is not gate-grade appear only in `e2e_cells`, never as blocking findings. It also emits `not_run_cells` = `[{"cell": "<ver>:<browser>", "reason"}]` for configured cells whose newest record is `not-run`. `e2e_browsers` = configured browsers; `e2e_browsers_run` = engines that drove in a selected record; `layers_run.e2e` = some configured cell has a record; `e2e_screenshot_dir` = the distinct run folders of the selected records' `screenshots` (a list, as today).

## Config keys

New keys get defaults in `.claude/skills/psm-setup/scripts/resolve-psm-config.py` `PSM_DEFAULTS`, like `psm_e2e_browsers` (no install prompt in `.claude/skills/psm-setup/assets/module.yaml`), and reach scripts via `--config`: `ps-aggregate.py` gains `--config`, and `ps-run-layer.py` gains `--config`, from which it reads, through its own key map (not `apply_config_file`, which would fill `--versions`), only the E2E keys below, the configured set, `psm_flashlight_startup_timeout` and `psm_flashlight_tag_map`; `--versions` stays required except for layer `e2e`. For every layer ps-run-layer forwards `--config` unchanged to each child itself. Explicit flags still win. **Image tag**: plan, runner and aggregate resolve it alike, `resolve_tag(parse_tag_map(--tag-map, else psm_flashlight_tag_map; --extra-tag-map), version)`; ps-run-layer takes both flags from its passthrough, and the orchestrator passes the same values to plan, ps-run-layer and aggregate. Values arrive as strings; an integer key that does not parse is an input error (exit 2).

- `psm_e2e_canary`: `<version>:<browser>`. Plan, runner and aggregate read it directly from `--config`, like the configured cells (no flag). Empty = newest of `psm_target_versions` (numeric order, see Configured cells) × `chromium` (first of `psm_e2e_browsers` when chromium is not configured). A canary outside the configured cells is an input error (exit 2).
- `psm_e2e_slots`: integer ≥ 1, default 6; below 1 is an input error (exit 2). Maps to `ps-run-layer.py --slots`. E2E only: Layers 2 and 5 keep `--jobs`; for layer `e2e` `ps-run-layer.py` admits work by slots. Costs: Parallel browsers > Slots (a container 1, each further concurrent browser 1). The cap covers the whole Docker daemon: the process that runs bring-up (the version process; the keeper for a warm container) stamps only its PS container (the compose `ps:` service, or the manual `docker run` of `ps_container`) with the label `psm.slots=<cost>` (its `--slot-cost`, Runner > Child flags; when absent, e.g. a direct `ps-e2e-run.py` run, the number of engines it drives in parallel, or 1 when it drives one engine or runs with `--sequential-browsers`), separate from `owner_labels()`, so the DB container, the network, Layer 2/5 containers, workers and iterations are never counted. Test: a compose boot and a manual boot each sum to exactly their cost; without `--slot-cost`, a two-engine parallel boot sums to 2 and a one-engine or `--sequential-browsers` boot to 1; a Layer 2 boot sums to 0. Before admitting a cell, `ps-run-layer.py` sums `psm.slots` over every running container on the daemon (`docker ps --filter label=psm.slots`, with `DOCKER_CMD_TIMEOUT` (120 s); with Docker absent the run is `skipped`, Runner > Output; any other failed or timed-out call counts as cap full), which every client sees: other sessions, other WSL distros, other temp dirs. Containers without the label (older scripts) are not counted. Every running labelled container counts, including an orphan whose owner died. Inside `wait-slots`, before its first count, ps-run-layer runs the `--cleanup-orphans` routine once, in every mode, interactive and headless (it removes only containers whose owner is provably dead on this host); the `ALIVE wait-slots` lines and the `no-slots` record list the counted containers by `psm.job` and owner host, so a foreign orphan can be cleaned from its owner. Admission holds `flock` on `<tmp>/psm-locks/slots.lock` across count-then-claim and also counts the `slot_claims` of every live ps-run-layer registry entry in `<tmp>/psm-jobs/` (its own included) whose container is not running yet: each ps-run-layer records its claims in its own entry (`slot_claims: [{run, cost}]`) and passes the pre-generated RUN_ID to the child or keeper as `--run-id`; a claim counts while no running container carries its `psm.run` and until its ps-run-layer has reaped that child, so a slot freed by a child's teardown is reused only after the fail-fast decision on its exit code. A claim from another temp dir becomes visible only once its container runs. A live warm container holds its slot between iterations; a warm iteration drives one cell and uses the keeper's slot.
  - When the cap is full, the cell waits in phase `wait-slots`, which emits the usual `ALIVE wait-slots` heartbeat lines, for at most the startup timeout (`--startup-timeout` in the passthrough, else `psm_flashlight_startup_timeout`, else 180 s), counted only while none of this invocation's own cells is in flight: a cell queued behind its own run's cells waits without limit. If no slot frees up in time, the cell is not started and gets a record with `state: inconclusive`, `conclusive: false`, `reason: "no-slots"`.
- `psm_e2e_warm_ttl`: idle minutes before the warm keeper tears down, integer ≥ 1, default 60. Maps to the keeper's `--warm-ttl`; ps-run-layer validates it at config load (exit 2, no keeper started).

## Headless

- The versions and browsers the caller passes (resolver defaults when it passes none) are the configured set: headless writes them as `psm_target_versions` and `psm_e2e_browsers` into a copy of the resolved config, `<psm_reports_dir>/<module>-psm-config.headless.<session>.json`, and forwards that file as `--config` to plan, runner and aggregate. When `psm_e2e_canary` names a cell outside that set, the copy sets it empty (default canary) and an `assumption` is logged. So `ready` and `versions` cover exactly the caller's cells.
- No warm container (see Warm container), and `e2e_scenarios` is always treated as `full`, so every headless E2E step leaves gate-grade evidence. The run drives the plan's steps in order and returns at the first step that is not clean: a step is clean when every cell in its `e2e_next_cells` has passing gate-grade evidence or is not-gradeable (Plan) after the run; `blocked-by-scope`, `blocked-not-gradeable` and `blocked-infra` are not clean. The stop ends only the E2E steps: every version's Phase 1 loop still runs its Layers 1, 2 and 5. Wherever it stops, it then runs the Phase 2 wrap-up (Plan > Phase 2; the Layer 3 lenses spawned first when it stops before Phase 2), so every return runs `ps-aggregate.py`, and the report says where it stopped.
- The return JSON gains `versions: {<ver>: {e2e_state, reason}}` and `not_run_cells`, copied from the aggregate run with this call's `--session`, except that a version with `reached: false` keeps the aggregate's `e2e_state` and, unless it is `fail`, gets reason `not reached: stopped at <step>`; and `e2e_tier_reached` = `{tier, step}` from the last plan call. Every early return (a step not clean, including an E2E job stopped by the silent-log rule, whose cells get `stopped`; `blocked-*`; E2E skipped) is `status: complete` with `ready: false`; `blocked` stays for "cannot assess at all" and for a stopped job of another layer.
