# E2E tier matrix

Defaults: canary = `psm_e2e_canary` (default newest target × Chromium, see `cell-contract.md` > Config keys); targets = `psm_target_versions`; browsers = `psm_e2e_browsers`. "Canary browser" below is the canary's browser; "other browsers" are the remaining configured browsers.

| Tier | Phase | Cells | Boot | Scenarios | Starts when | Evidence counts for |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | Fix loop (Phase 1) | focus cell: the canary, or after a loop-back the failed cell (V, browser); see Loop-back | cold while the focus cell has no recorded failure; after a failure warm (CAP-5, interactive only); cold for the promotion runs | full while the focus cell has no recorded failure; after a failure failed-only (CAP-4) or full; promotion runs full | every patch, inside the hosting version's Phase 1 loop (`cell-contract.md` > Plan > Phase 1) | warm/partial runs: convergence only; cold full runs: gate |
| 1 | Release gate (Phase 2) | every configured cell that neither has passing gate-grade evidence nor is not-gradeable: each non-canary version × all configured browsers, plus the canary version × other browsers | cold, one boot per version, browsers parallel (CAP-7) | full | every version clean on Layers 1, 2, and 5 and tier 0 clean (canary has passing gate-grade evidence or is not-gradeable, and no cell is failing) | gate |

Rules:

- Tier 0's last run before promotion is a cold full-scenario run, so tier 0 also leaves gate-grade evidence for the canary cell.
- A focus cell with no recorded failure (`cell-contract.md` > Plan) gets a cold full-scenario run, never a warm or failed-only one. On a clean module the first canary run is therefore already gate-grade, and the canary version boots twice in total: the cold canary run and its tier 1 boot for the other browsers.
- The canary version boots in tier 1 only for its other browsers, because tier 0 already left its canary-browser cell gate-grade. Each version boots at most once in tier 1.
- **Loop-back.** A failure in tier 1 at (V, browser) returns the loop to tier 0 with that cell as the focus cell. Steps, in order: (1) fix-loop iterations on the focus cell (warm when interactive, failed-only allowed) until it passes; (2) one cold full-scenario run of V with all its configured browsers in one boot (CAP-7); (3) one cold full-scenario canary run; (4) tier 1 (cells as in the table). A failure in step 2 or 3 makes the failing cell the new focus cell and restarts at step 1. With several failing cells, steps 1 and 2 run for each in focus-cell order, and step 3 runs once no non-canary cell is failing. When V is the canary version, step 2 already covers the canary cell and step 3 is skipped. When the focus cell is the canary itself, step 2 is skipped. The canary itself stays `psm_e2e_canary`. The plan derives the step from the records, first match wins (`cell-contract.md` > Plan).
- Fail-fast (CAP-3) applies within each tier.
- `ps-plan-layers.py` owns the tier order (`e2e_tier`, `e2e_next_cells`). Promotion to the next tier is automatic in interactive and headless runs. A headless run takes its configured cells from the caller's versions and browsers, never uses a warm container or failed-only scenarios (tier 0 runs cold and full), and stops at the first step that is not clean, reporting `e2e_tier_reached`.
- A tier is **clean** when every cell in it has passing gate-grade evidence (`cell-contract.md`), or, for promotion only, is not-gradeable (`cell-contract.md` > Plan). So a smoke-only module, or one whose specs carry notes, still runs tier 1 once and every configured cell gets the universal smoke; results are reported and `ready` stays false. An inconclusive cell (boot timeout, missing image, install failure, launch error), or a pass with inconclusive steps (e.g. BO login failure), blocks promotion: report the infra cause and rerun that cell. When a cell's two newest records on the same fingerprint in one validation session both have an infra cause, whatever the causes (a `stopped` record is skipped, not counted), the plan reports `e2e_step: blocked-infra` and the E2E loop ends (`cell-contract.md` > Plan > E2E loop ended).
- An empty tier 1 (one target version and one configured browser) is clean for promotion only. It never makes `ready` true for a configured cell that did not run.
- Tiering orders only Layer 4 cells. Phase 1 per-version convergence gates only Layers 1, 2, and 5 (`phase1_reuse`, `cell-contract.md` > Plan). Tier 0 runs inside the Phase 1 loop of the hosting version (the focus cell's version on entering Phase 1, so the canary's unless a cell is failing), which runs first, and that loop ends only when its version is clean on Layers 1, 2, and 5 and `e2e_step` is `gate` or `done` or the E2E loop has ended (`cell-contract.md` > Plan). Phase 2 starts when every version's Phase 1 loop has ended and a fresh plan call confirms it (`cell-contract.md` > Plan > Phase 2 entry); a patch made in any loop reopens the versions it staled. Tier 1 runs in Phase 2, after source stops being patched, and Layer 3 lenses spawn at the start of Phase 2 as today. The operator action "stop convergence" ends every Phase 1 loop without running tier 1 (`cell-contract.md` > Plan > Stop convergence). A loop-back to tier 0 re-enters Phase 1: Layer 3 results not yet merged are discarded, never merged after the patch, and the lenses spawn again at the next Phase 2.
- Run scope (`--versions`, `--browsers`, the scope menu) filters each step's cells and never reorders the tiers. When the filter leaves nothing, nothing runs and the plan reports `e2e_step: blocked-by-scope` with the required cells (`cell-contract.md` > Plan).
- **Visual review** (Layer 4, interactive only as today): the orchestrator reviews screenshots only of cold full-scenario runs (the cold canary run and tier 1; after a loop-back also `cold-version` and `cold-canary`), never of warm or failed-only runs. A defect it judges blocking goes into `findings` of `<module>-adversarial.json` by read-merge as today, but only after the current Phase 2's Layer 3 merge (or at Phase 2 start when the plan reuses Layer 3); until then it waits in `<psm_reports_dir>/<module>-visual-pending.json` (same `findings` shape, each entry tagged with `session` and the run's `source_fingerprint` from ps-run-layer's output line, written by read-merge), which the orchestrator merges, dropping entries of another session or a fingerprint other than the plan's current `source_fingerprint`, then deletes, so a visual write never makes stale Layer 3 output look fresh. It never changes a cell's state and never triggers an E2E loop-back.
- `ready` = every configured (version, browser) cell has passing gate-grade evidence (`cell-contract.md`; CAP-2).
