- (direction) Budi: E2E across 3 versions x 2 browsers takes a whole day; proposes 9.x+Chrome first, other versions and Firefox only after it is clean; open to other ideas.
- (note) Current: ps-e2e-run boots one PS+DB container per version, runs browsers sequentially inside it; ps-run-layer --jobs (default 3) parallelizes versions; one source patch stales every version via mtime.
- (note) Gap found: ps-plan-layers prov_for (e2e) compares image tag only, not browser set — chromium-only evidence would read as fresh and Firefox would never run at the gate.
- (decision) Scope chosen by Budi: tiered gate, warm container in fix loop, per-phase timing, fail-fast + failed-only rerun. Firefox at release gate runs in parallel with Chromium in one boot.
- (capability) CAP-1 tiered E2E gate: tier0 canary version x chromium during fix loop; tier1 other versions x chromium; tier2 firefox on all versions at release gate; promotion only when prior tier is clean.
- (capability) CAP-2 browser-aware freshness: e2e evidence fresh per (version, browser); ready=false unless every configured browser has fresh conclusive full-scenario evidence on every target version.
- (capability) CAP-3 fail-fast: first conclusive blocking E2E finding stops not-yet-started (version, browser) work; skipped cells reported not-run, never pass.
- (capability) CAP-4 failed-only rerun: in fix loop, rerun only scenarios that failed in latest evidence for that version; subset evidence is partial and never satisfies the gate.
- (capability) CAP-5 warm canary container: fix-loop container stays up across iterations, module changes reach it without reboot, reinstall + DB reset to post-boot baseline per iteration; owned by a Job ID.
- (capability) CAP-6 per-phase timing: durations for bring-up, wait-healthy, install, each browser recorded per version in layer JSON and surfaced in aggregate report.
- (capability) CAP-7 parallel browsers per boot: when a version needs both browsers, they drive concurrently against one container.
- (assumption) Canary defaults to newest target (9.1) + chromium, configurable; Budi named 9 + Chrome.
- (assumption) Release-gate evidence always comes from a cold boot; warm-container evidence counts for convergence only, because warm state can mask install-path bugs.
- (assumption) Fail-fast does not kill in-flight cells; it only stops unstarted ones (in-flight killing risks orphaned state).
- (assumption) Tiering applies equally to headless callers (psm-develop, psm-cross-version, psm-scaffold, psm-optimize); their per-version verdict contract is unchanged.
- (question) Parallel browsers share one DB: scenarios mutating global BO config (e.g. bo-setup-country) can race. Serialize such scenarios, or require scenarios to declare isolation?
- (question) Is there a target wall-clock budget for a fix-loop iteration and for the full release gate?
- (question) Should the canary follow the version that last failed instead of staying fixed at 9.1?
